# 项目审查报告（2025-12）

> 审查范围：前端流畅性 / 性能、网页 UI 自适应（响应式）、后端架构与安全、Fairy AI 全面接管能力。
> 方法：全量代码走查（app/、netlify/、zzzui/）+ 三路并行深度审查，所有问题均给出文件定位与修复建议。
> 优先级：P0 严重（直接影响体验/安全）→ P3 轻微。

---

## 一、前端流畅性与性能（25 项，摘录 Top 10）

项目已有大量正确的性能基建（虚拟瀑布流、rAF 节流、no-gpu 降级、缓存预填、已读回填延迟、backdrop-filter 预热等），以下为仍存在的问题：

### P0

1. **`app.vue:2` 静态导入 PostOverlay（99.8KB）** — 连同其 8 个子组件全部打进主入口 chunk（产物约 115.6KB min）。首页首屏关键路径过重。虽注释说明异步组件会让入场动画错过首帧，但可改为「同步占位 + 空闲预取 chunk」：`v-if` 挂载前用 `requestIdleCallback` 预载组件模块，兼顾首帧与体积。

2. **首页请求风暴（`pages/index.vue:472`）** — `deleted-since` 每 8s 轮询 + 60s 新帖轮询 + Tab 回前台全量 `invalidateQueries`（`plugins/cache-revalidation.client.ts:28`）。移动网络下持续占带宽、触发列表重排。建议 deleted-since 间隔提到 15~30s，回前台失效改为只失效 feed 相关 key。

3. **敲敲弹窗 5s 轮询无可见性门控（`useDmConversations.ts:1064`）** — 弹窗开着但切到后台 Tab 时仍每 5s 重拉会话列表 + 强制重拉当前会话消息，白耗带宽与主线程。建议轮询回调先检查 `document.visibilityState === "visible"`。

4. **VirtualMasonry `containerOffsetY` 陈旧（`VirtualMasonry.vue:300`）** — 仅在 mount / 容器 resize 时更新；公告条等上方内容异步出现/消失后，虚拟窗口相对文档的偏移失效，滚动出现空白区或重复渲染。建议用 ResizeObserver 观察容器父级（或 body），高度变化时重算 offset。

### P1

5. **桌面端全屏 `backdrop-filter` 常驻** — `html.no-gpu` 已有降级，但 GPU 路径下部分弹窗遮罩全屏模糊仍会拖慢低端 GPU 滚动；建议弹窗滚动期间暂停遮罩模糊（已有部分处理，可扩展）。
6. **PostCard 封面 `will-change` 滥用** — 虚拟列表反复挂载/卸载卡片时，永久 `will-change: transform` 会堆积合成层；建议仅在 hover/入场期间临时启用（需核对 `PostCard.vue` 具体写法）。
7. **KnockKnockModal 滚动监听未节流** — 4190 行巨型组件的滚动回调（`is-mobile-chat` 切换、加载历史等）未统一走 rAF，滚动期间可能有额外 layout 计算。
8. **评论区不虚拟化** — 长帖（数百评论 + 楼中楼）一次性渲染全部 CommentItem；每项还实例化 useEmotes 等 composable。建议首屏只渲染前 N 条 + 懒渲染剩余（简单 IntersectionObserver 分批即可，不必上完整虚拟列表）。
9. **`v-memo` 依赖不完整** — 部分列表项 v-memo 未把用到的全部响应式字段列入，导致命中失效，需逐项核对。
10. **markdown-it 高亮重复执行** — `useRenderedBody` 已按需加载，但同一 postId 切换弹窗/详情时 bodyHtml 重新渲染；可加 per-postId 缓存。

### 建议保持不动（防回归）

虚拟化裁剪、rAF 节流滚动、no-gpu 降级、缓存预填（peekArticles）、已读回填延迟、backdrop-filter 预热、卡片高度估算体系、跨实例封面加载缓存——这些已做对，改动需谨慎。

## 二、网页 UI 自适应（响应式）（16 项，Top 10）

### 断点现状（15 个互不相同的值）

| 断点 | 出现次数 | 主要用途 |
|------|---------|---------|
| 768px | 17 | 全局移动端（JS/CSS 主断点） |
| 500px | 13 | 弹窗全屏化 |
| 1024px | 10 | 平板档（弹窗、header tabs） |
| 1280px | 4 | 宽屏收窄 |
| 1100/1180/1200/1400 | 各 1-2 | 历史遗留中间值 |
| 900/800/600/1023 | 各 1-3 | admin / create 专用断点 |

### P0

1. **后台表格无横向滚动容器（`app/pages/admin/*.vue` + `admin.css`）** — 平板（769~1024px）下 7 列表格挤压换行、页面出现横向滚动。建议统一给表格包 `<div class="ik-admin-table-scroll">`（`overflow-x: auto`），并在窄屏隐藏次要列（时间、作者列）。
2. **`.ik-page` 底部 padding 不足（`theme.css:400-402`）** — 移动端 `padding-bottom: 64px` < MobileBottomNav 高度（`58px + env(safe-area-inset-bottom)`），iOS 底部内容被遮挡。改为 `calc(58px + env(safe-area-inset-bottom) + 12px)`。

### P1

3. **断点碎片化（JS 768/900/1024 vs CSS 800/1023/1100）** — JS 与 CSS 断点口径互不统一，组件行为与样式在不同宽度下"打架"。建议收敛为 4 档：`≤768 / ≤1024 / ≤1280 / >1280`（CSS 用 767.98/1023.98 保连续），逐步迁移。
4. **admin 侧边栏 1024px 折叠为图标（`layouts/admin.vue:359`）** — 已实现，但内容区表格仍溢出；与 #1 配套。
5. **create 页移动端与桌面端双套 UI（`pages/create.vue`）** — 桌面 `grid` 布局 + 移动端独立 Flutter 风格扁平 UI（`ik-create-mobile-*`），模板/样式几乎不共用，维护成本翻倍（设计文档已给出统一方案，建议按 P1~P4 分期重构）。
6. **zzzui modal/drawer 固定像素宽度** — `z-modal` 的 `width` 是 px 硬编码，小屏下弹窗超宽；建议库内加 `max-width: calc(100vw - 24px)` 兜底。
7. **PostOverlay 移动端键盘遮挡** — 底部操作栏已用 `--vv-bottom`，但部分场景（评论输入框聚焦）未跟随 visualViewport 更新，需核对 `useVisualViewport` 使用覆盖。
8. **安全区遗漏组件** — `LoginDialog` / `ConfirmDialog` / 部分弹层未加 `env(safe-area-inset-bottom)`（移动端底部按钮被 Home 条遮挡）。
9. **悬停卡在窄桌面（769~1024px）仍触发** — `useHoverCapable` 用 `min-width: 769px` 判定，平板横屏 + 触屏设备会误判；建议叠加 `(hover: hover)` 已含，确认 `pointer: coarse` 覆盖。
10. **搜索联想浮层宽度固定** — 小屏下超出视口，建议 `max-width: min(360px, calc(100vw - 24px))`。

### 断点统一建议

```css
/* 移动端 */  @media (max-width: 767.98px)
/* 平板 */   @media (min-width: 768px) and (max-width: 1023.98px)
/* 小桌面 */ @media (min-width: 1024px) and (max-width: 1279.98px)
/* 宽屏 */   @media (min-width: 1280px)
```

## 三、后端架构与安全（重点）

### P0 高危

1. **GLM API key 硬编码（`glm.ts:3`）** — `GLM_API_KEY` 明文写在源码且已提交；`netlify.toml` 注释声称的环境变量覆盖实际不生效。建议：源码改读 `process.env.GLM_API_KEY`，密钥移到 Netlify 后台 Environment variables（scope 含 Functions），并在仓库删除历史中的密钥。
2. **JWT_SECRET 兜底弱密钥（`auth.ts:7`）** — 缺失时回退 `"dev-only-change-me"`，可被用于伪造管理员 token。建议生产环境启动时校验并拒绝弱密钥（或至少 `console.warn` + 文档强调）。
3. **每个 API 请求都执行 `ensureSeed()`（`api.ts:30` + `seed.ts`）** — 每个请求多 2 次 blob GET（settings + meta）。建议用模块级 `Promise` 缓存（进程内只跑一次）或只在管理写接口后置标记。
4. **feed.json 全量 CAS 重写（`feed.ts` + `articles.ts:80-84`）** — 每次点赞/评论/浏览都重写含正文的 feed 索引（≤1000 条，MB 级）。浏览量尤其高频。建议浏览量改独立计数文档（如 `_indexes/views/{postId}.json`），feed 只存轻量摘要字段。
5. **列表页 N+1（`articles.ts` viewerState + `serialize.ts` hydrateAuthorLevels）** — 登录用户每页约 80+ 次 blob 操作（3×N HEAD + N 次用户文档读）。建议：`viewerState` 批量改为一次 `listKeys` 或合并 exists；作者快照直接信任 feed 内嵌字段，仅对异常（作者不存在）做 hydrate。
6. **评论 @fairy 同步阻塞（`comments.ts:231-275`）** — 评论 POST 内同步调 GLM（2~10s），请求挂起且可被刷接口拖垮。建议改为异步任务（Netlify Background Functions / 队列）+ 前端轮询结果，或至少限流。

### P1

7. **全局 listKeys 扫描** — `follows/`、`users/`、`uploads/`、`dm/conv/`、`notifications/` 多处全前缀扫描（admin stats 一次开后台 = 全库遍历）。数据量上来后不可持续，建议为高频路径维护反查索引（已有 `_indexes/` 体系可扩展）。
8. **`admin.ts:400,629` 删评论清空用户索引 bug** — 删除单条评论会清掉该用户全部评论索引（`KEYS.userComments` 整体覆盖）。需改为「过滤 + 写回」。
9. **`updateUserStats` 无 CAS** — 并发（点赞+评论同时）可能丢计数。建议沿用 feed 的 `getJsonWithEtag + setJsonIfMatch + 重试` 模式。
10. **presencePing 每心跳全量扫描（`stubs.ts`）** — 每个在线用户每 20s 全表扫一次 presence 会话。建议改为「按 presenceId 单点读写 + 定期 GC」。
11. **全站无速率限制** — 登录、评论、发帖、AI 对话均无限流。建议对高频写接口做 blob 令牌桶。
12. **GLM 调用无超时上限** — `fetch` 无 AbortSignal，弱网下 sendMessage 可能挂很久；建议 30s 超时 + 错误提示。

## 四、Fairy AI 全面接管博客（方案摘要）

现状：Fairy 仅能聊天（`ai.ts` 同步回复）与评论区 @回复；前端已有完整的 AI 工作流时间线展示（`AiReasoningBlock` / `AiReasoningTimeline` / `AiCitationList` / `AiRelatedPosts` + `workflow.ts` 事件协议），但后端从不产生 workflow 事件 —— 基建闲置。

**核心方案：工具调用（function calling）**

- **架构**：`ai.ts sendMessage` 收到用户消息 → 构造带工具定义的 GLM 请求 → GLM 返回 `tool_calls` → 执行器按「当前请求用户」身份执行工具（合成 Request 复用现有路由，鉴权/归属/计数零重复）→ 把 `tool.start/finish` 等事件写入 `aiReply.workflow` 落库 → 前端现有时间线组件自动展示。
- **工具清单**：
  - 浏览类（游客可）：`search_posts` / `get_hot_posts` / `get_post_content` / `get_post_comments` / `get_user_info` / `get_site_stats` / `get_categories`
  - 操作类（需登录，以用户身份）：`publish_post` / `reply_comment` / `like_post` / `favorite_post` / `follow_user`
  - 管理类（需管理员）：`admin_delete_post` / `admin_hide_post` / `admin_pin_post` / `admin_process_report` / `admin_update_settings` / `admin_list_reports`
- **安全**：工具参数 schema 校验、每轮上限（maxToolRounds=3）、工具结果裁剪 + prompt injection 包裹、敏感操作由权限层拦截、审计日志。
- **阶段**：P0 后端 executor/工具表/GLM 改造 → P1 前端工具卡片（复用现有时间线）→ P2 限流/二次确认/审计 → P3 定时任务、SSE 流式、长期记忆。

（详细设计见子文档 `docs/Fairy接管设计.md`，实施中逐步落地。）
